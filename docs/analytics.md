# GA4による会社・製品ページの計測

会社サイト、製品LP、schedulaの公開デモ・技術案内は、同じGA4プロパティの一つのWebストリームを使う。配信元やコードrepoによってプロパティを分けない。

## 接続に必要な設定

1. Google Analyticsで会社管理のアカウントとGA4プロパティを作成する。レポートのタイムゾーンは日本、通貨は日本円にする。
2. Webストリームを`https://the3.co.jp`で作成し、`G-`から始まる測定IDを取得する。
3. このrepoと`the3-inc/schedula`の両方のActionsのRepository variablesに、同じ`PUBLIC_GA4_MEASUREMENT_ID`を登録する。公開IDなのでSecretsではない。schedulaはproduction承認前のbuildジョブで使うため、Environmentだけに登録しない。
4. 拡張計測は項目ごとに設定する。スクロールは有効でよい。フォーム操作と「ブラウザーの履歴イベントに基づくページの変更」は無効にする。外部リンク・ファイルダウンロードは、収集されるリンク先URLに個人情報や秘密がないことを確認してから有効にする。サイト内検索・動画は導入時に必要性を判断する。Googleシグナル・広告のパーソナライズ・ユーザー提供データの収集は有効にしない。通常のページ閲覧・ユーザー・エンゲージメントは公式タグで計測する。
   自動の`form_submit`は送信操作の検知であり、受付成功を保証しない。今回の問い合わせ完了は受付成功後の`generate_lead`だけで判定する。別名のイベントなので、併存しただけで同じイベントが二重になるわけではない。
5. 内部トラフィックの定義を会社の実際の接続元に合わせ、まずテスト状態で確認してから除外を有効にする。開発・プレビューURLでは、タグがあってもGoogleへ送信しない。
6. イベント単位のカスタムディメンション`lesson_id`、`operation`、`result_status`、`form_id`を登録し、`generate_lead`をキーイベントにする。
7. 通常のタグ公開で両repoを配備する。hardened構成では、先にinfraのGA4用CSP変更を適用する。受付先が未設定でもページ・デモの計測は開始できる。問い合わせ完了は、下記の受付先の接続・確認後に開始する。

測定IDが未設定・不正な場合、新しい公開workflowはAWS更新前に停止する。通常のローカルビルドではIDの省略を許可し、Googleタグを入れない。IDを設定したローカルビルドも、`https://the3.co.jp`以外では計測しない。

## 問い合わせフォームの受付先

受付サービスは未選定。送信先を決めるまではフォームを公開せず、既存のメール・電話窓口を維持する。
選定後、production Environment variableの`PUBLIC_CONTACT_ENDPOINT`に公開のHTTPS受付URLを登録する。秘密キーやパスワードを含むURLは使わない。

受付先は以下の契約を満たすサービスを選ぶ。合わないサービスはその仕様に合わせた接続変更が必要であり、URLを設定しただけで接続済みとはしない。

- ブラウザーから`multipart/form-data`のPOSTを受け付ける。フィールドは`name`、`email`、`message`。
- `Accept: application/json`に対応し、クロスオリジンの場合は`https://the3.co.jp`からのCORSを許可する。
- **実際に受け付けた場合だけHTTP 2xxを返す。** 入力エラー・迷惑送信・受付失敗は非2xxを返し、ログイン・確認画面へのリダイレクトや「HTTP 200だが受付失敗」の応答を返さない。
- サーバー側の入力検証、迷惑送信対策、通知先・保存期間・閲覧権限を設定する。HTMLの入力制限だけで受付を保護しない。

送信中はボタンを無効化し、成功後はフォームを無効のままにする。失敗時は入力を残し、成功イベントを送らない。タイムアウト・通信断では受付側だけが完了している可能性があるため、再送で重複することがある。受付成功はメールの到達・担当者の対応完了とは区別する。
JavaScriptが無効な場合は受付サービスへの通常POSTになり、GA4の完了イベントは送られない。

## 指標とイベント

| 対象 | 計測 |
| --- | --- |
| 全HTMLページ | Google公式タグの自動`page_view`と`user_engagement` |
| 利用者が明示的に再計算・再検証し、有効な結果を受理した操作 | `demo_run_success`。`lesson_id`、`operation`、`result_status`を送る |
| 問い合わせ受付先がPOSTにHTTP 2xxで応答 | `generate_lead`。`form_id=contact`だけを送る |

デモの初期表示・教材選択時の自動計算・初期値への復元による自動計算は成功イベントに含めない。
独立検証が成功した`PARTIAL`は操作成功に含めるが、需要の完全充足とは区別して`result_status`で分析する。
APIエラー、無効な応答、入力不備、無効な計画、古い入力に対する応答は成功に数えない。
メール・電話のクリックは問い合わせ完了ではない。

標準の「ページとスクリーン」でページパス別に「表示回数」「総ユーザー数」「アクティブユーザーあたりの平均エンゲージメント時間」を表示し、日・週・月と前期間を比較する。
総ユーザー数は選択期間内の識別子に基づくユニーク数で、実人数や端末横断の同一人物を保証しない。ページ別の人数を足して全体の人数にはしない。
平均エンゲージメント時間は前面での利用時間をアクティブユーザー数で割った値であり、ページを開いてから閉じるまでの経過時間ではない。

探索ではLP閲覧→デモ閲覧→`demo_run_success`、問い合わせページ閲覧→`generate_lead`を同一ユーザー・順序指定で集計する。
イベント回数と、イベントを起こしたユニークユーザー数は別の指標にする。
API・画像・生Markdown・ライセンスファイルはHTMLページではないため、閲覧時間の対象外。技術案内のHTMLページは対象。

## データの範囲と検証

独自イベントに氏名・メール・問い合わせ本文・デモ入力・実行識別子を入れない。拡張計測で有効にする自動イベントは別に送信内容を確認し、特に`link_url`・`form_destination`等のURLを確認する。`page_location`と`page_referrer`からqueryとfragmentを除く。このため、URLのUTMによるキャンペーン別分析は今回の実装対象に含めない。
Googleシグナルと広告パーソナライズもコードで無効化する。計測時はページ下部にGoogle Analyticsの利用と無効化方法を表示する。
対象地域・運用に応じた同意取得が必要な場合は、測定IDを本番へ設定する前に同意の仕組みを接続する。現実装は本番ホストでIDが設定されるとCookieを使った計測を開始する。

公開前に、ブラウザーで次を確認する。受付サービスにはテスト問い合わせを送れることを確認してから行う。

1. 会社5ページと製品のデモ・技術案内を開き、Networkで各遷移につき`page_view`が一度だけ送られ、両repoが同じ測定IDを使うことを確認する。
2. ページを前面で閲覧して別ページへ移り、GA4のリアルタイム/DebugViewで`user_engagement`と`engagement_time_msec`を確認する。独自タイマーは追加しない。
3. デモの自動初期計算ではイベントがなく、再計算成功では`demo_run_success`が一度、無効な手修正の再検証ではゼロになることを確認する。
4. フォームの受付失敗では`generate_lead`がゼロ、受付成功では一度だけになることを確認する。受付側の記録・通知も照合する。
5. Networkの送信内容にフォーム入力やquery/fragmentがないこと、プレビュー環境から送信しないことを確認する。

GA4への受信確認と標準レポートへの反映確認は別々に記録する。広告ブロック、同意状態、通信切断で欠測がある。IDと受付先の未設定状態・ローカルのモック成功だけでは本番計測完了としない。
